# GitHub Actions cache specification

- Status: accepted for M16A
- Last updated: 2026-09-04

## Purpose

GitHub-hosted runners are ephemeral. The release workflow therefore persists
download and build caches in GitHub Actions cache storage while preserving an
independent cache-cold proof. A cache is an optimization only: it MUST NOT
change generated bytes, remove a test, or turn a failed semantic check into a
successful job.

GitHub cache entries are immutable. A successful workflow MUST publish a new
key and later workflows MUST restore the newest compatible prefix match. Bazel
disk-cache entries are content addressed; repository-cache downloads are used
only when Bazel can identify the expected content. These properties permit
reuse across source commits without making source hashes part of the cache
compatibility prefix.

Normative references:

- [GitHub dependency caching reference](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching)
- [Bazel remote and disk caching](https://bazel.build/remote/caching)
- [Bazel repository cache](https://bazel.build/versions/7.0.0/run/build#the-repository-cache)

## Cached paths

Only paths outside the checkout may be persisted:

- Bazelisk downloads;
- Bazel repository downloads;
- Bazel action/disk-cache outputs;
- Cargo registry and Git checkout caches; and
- the pinned Cargo tool installation root.

The cache MUST NOT contain source, generated manifests, credentials, test
results, Bazel output-base state, or a compiler server.

## Compatibility and rotation

The cache prefix MUST include:

- a schema/version owned by this repository;
- the runner operating system; and
- a hash of the Cargo lock, Bazel module and lock, development image,
  Bazel version, and Bazel configuration.

The primary save key MUST additionally include `github.run_id` and
`github.run_attempt`. This makes every successful execution capable of saving
an updated immutable cache. `restore-keys` MUST contain only the matching
compatibility prefix, causing GitHub to select its newest compatible entry.

Changing a toolchain, dependency lock, container image, Bazel version, Bazel
cache configuration, or cache layout MUST select a new compatibility lineage.

## Cold and warm proof

The release job owns two disjoint directory trees:

- an ephemeral cold tree which is freshly removed, recreated, and asserted
  empty immediately before the cache-cold release gate; and
- a persistent tree restored from GitHub and used only by the cache-warm
  release gate.

The cold tree MUST never appear in the cache action's path list. The cold gate
MUST NOT delete or populate the persistent Bazel directories. The warm gate
MUST execute the same complete release script even on a cache hit; cached
results may avoid work but may not skip commands or targets.

The cache is saved only after both gates succeed. Cache restore failure or
absence falls back to a complete uncached warm execution and MUST NOT weaken
the job.

## Required evidence

- A repository policy test checks cache paths, rotating key components,
  compatible restore prefix, disjoint cold/warm mounts, and the empty-cold
  assertion.
- Actionlint accepts the workflow.
- The full local release gate passes in the Linux development container.
- One hosted run populates the new cache lineage and passes both release
  gates.
- A later hosted run reports restoration of that lineage and again passes
  both gates; its cache-cold gate remains independent.
