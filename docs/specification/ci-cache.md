# GitHub Actions cache specification

- Status: accepted for M16A and M16B
- Last updated: 2026-09-04

## Purpose

GitHub-hosted runners are ephemeral. The release workflow therefore persists
download and build caches in GitHub Actions cache storage. A cache is an
optimization only: it MUST NOT change generated bytes, remove a test, or turn
a failed semantic check into a successful job.

GitHub cache entries are immutable. A successful workflow MUST publish a new
key and later workflows MUST restore the newest compatible prefix match. Bazel
disk-cache entries are content addressed; repository-cache downloads are used
only when Bazel can identify the expected content. These properties permit
reuse across source commits without making source hashes part of the cache
compatibility prefix.

Normative references:

- [GitHub dependency caching reference](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching)
- [Bazel remote and disk caching](https://bazel.build/remote/caching)
- [Bazel repository cache](https://bazel.build/versions/7.0.0/run/build#the-repository-cache)

## Cached paths

Only paths outside the checkout may be persisted:

- Bazelisk downloads;
- Bazel repository downloads;
- Bazel action/disk-cache outputs;
- Cargo registry and Git checkout caches;
- the pinned Cargo tool installation root;
- pinned Node package tools; and
- the pinned Python virtual environment.

The cache MUST NOT contain source, generated manifests, credentials, Bazel
output-base state, a compiler server, or independently archived test reports.
Bazel's own content-addressed action and test-result entries are permitted and
remain subject to Bazel's action-key validation.

## Compatibility and rotation

The cache prefix MUST include:

- a schema/version owned by this repository;
- the runner operating system; and
- a hash of the Cargo lock, Bazel module and lock, Bazel version,
  configuration, and native bootstrap scripts.

The primary save key MUST additionally include `github.run_id` and
`github.run_attempt`. This makes every successful execution capable of saving
an updated immutable cache. `restore-keys` MUST contain only the matching
compatibility prefix, causing GitHub to select its newest compatible entry.

Changing a toolchain, dependency lock, native bootstrap, Bazel version, cache
configuration, or cache layout MUST select a new compatibility lineage.

## Cached release gate

The release job MUST restore the persistent cache tree before running exactly
one complete release gate. Bazel MUST remain responsible for deciding whether
each action or test result matches its declared inputs, toolchain, execution
configuration, and command line.

The workflow MUST NOT run a second cache-cold copy of the release gate. Cache
restore failure or absence naturally makes the single release invocation
populate an empty persistent tree. The cache is saved only after that gate
succeeds.

## Required evidence

- A repository policy test checks cache paths, rotating key components,
  compatible restore prefix, single-gate execution, and save ordering.
- Actionlint accepts the workflow.
- The full local release gate passes in the Linux development container.
- One hosted run reports restoration of a compatible cache lineage and passes
  the single cached release gate directly on Linux without Docker.
