# M24 — Language package IR and dynamic imports

- Status: in-progress
- Phase: 8
- Depends on: M08, M14, M21, M22A, M22B foundation checkpoints

## Outcome

Separate target translation from source rendering. Every required backend lowers
checked PolyIR into a validated language package IR containing explicit file
groups, source files, dynamically collected imports, dependencies, and helpers.
A small language renderer consumes that package and cannot inspect checked
PolyIR.

The pipeline becomes:

```text
CheckedProgram
    -> target language plugin / flat semantic mappings
    -> LanguagePackage<target import IR>
    -> target syntax renderer
    -> OutputManifest
```

## Implementation checklist

- Add a public generic language-package model without changing the frozen v0
  `Backend` entry point.
- Represent deterministic file groups and file roles explicitly.
- Represent each source file as preamble, collected imports, body, and epilogue.
- Deduplicate and sort import requirements before target syntax rendering.
- Define a language plugin contract whose translation stage sees checked IR and
  whose renderer stage does not.
- Reject duplicate groups, duplicate paths, invalid paths, and rendering-limit
  failures before filesystem materialization.
- Migrate Python first and prove imports are present exactly when their mapped
  constructs require them.
- Migrate Rust, Go, TypeScript, JavaScript, Java, C++, and C; remove static import
  or include blocks from their translated source assembly.
- Preserve deterministic generated bytes except where removing unused imports or
  normalizing import ordering is the intended change.
- Update the backend author guide and architecture diagram with the new layer.

## Required exit evidence

- Unit tests prove file-group ordering, import sorting/deduplication, empty-import
  omission, group/path collision rejection, and renderer error propagation.
- Each required target has focused tests showing at least one import/include/use
  appears when required and disappears from a program/file that does not require
  it.
- No target renderer accepts `CheckedProgram`; compile-fail documentation proves
  the boundary.
- All generated packages still pass their native formatter/linter/static,
  compiler, test, conformance, and sanitizer gates.
- Three complete generations are byte-identical.
- `bazelisk test //... --test_output=errors` and
  `bazelisk test //:release_gate --test_output=errors` pass in the Linux
  development container, including Buildifier, Rustfmt, and Clippy.

## Scope boundary

M24 introduces package- and source-file-level language IR plus structured import
requirements. Target declaration and expression nodes may initially be retained
as structured `Document` bodies while they are moved behind the translation
boundary. A later milestone may deepen each plugin's language AST without
changing the package, grouping, import, renderer, or manifest contracts.

The outer `Backend::generate(CheckedProgram) -> OutputManifest` API remains
compatible for external backends. Existing backends must not bypass the new
translation/rendering path after their migration checkpoint.

## Foundation and Python checkpoint evidence

- `polyrust-codegen` now exposes sorted `LanguagePackage`, `FileGroup`, file
  roles, grouped `ImportSet`, source sections, `LanguagePlugin`, and the
  checked-IR-free `LanguageRenderer` contract.
- Package tests cover import sorting/deduplication, omission for an empty import
  set, deterministic group/file flattening, invalid/empty/duplicate groups,
  duplicate paths, renderer failures, and the compile-fail stage boundary.
- Python is the first fully migrated backend. Its generated module, runtime,
  portable tests, conformance test, and negative test all declare imports as
  file-local requirements; the renderer merges names by module and the checked
  runtime template no longer contains a static import block.
- A feature-bearing checked fixture requires dataclasses, protocols, and casts,
  while an empty checked module emits only the `json` and `Runtime` imports its
  bootstrap actually uses. The former blanket `# noqa: F401` imports are gone.
- The Python unit/native gates, Buildifier, Rustfmt, and Clippy pass. The full
  repository gate passes 138/138 tests, including regeneration, determinism,
  every native target, all differential ports, C/C++ sanitizers, and release
  policy checks.
